# Crew 0.4.1

Configure one application-wide Grok webhook in Crew's browser UI. An existing
agent also acts as dispatcher: it handles work addressed to itself and hands
other tasks to their mapped Grok Bots. No extra dispatcher bot or per-agent
webhook credential is required.

The owner copies the URL and secret from Grok's routine UI directly into Crew.
They are never returned through MCP. The shared MCP connection manages the
non-secret dispatcher instructions and bot mappings. Instructions are versioned;
Crew distinguishes a reported application from matching routine text supplied
for verification. This is synchronization evidence reported by the caller, not
an independent connection to Grok's routine management API.

Ready task notifications carry explicit recipients. Durable execution coordination
checks current task state, generation, restore epoch and routing before work.
Dispatch, execution and transport results remain separate. Duplicate acquisition
is refused; ambiguous handoff or execution failures require deliberate recovery.
This does not guarantee exactly-once effects in external systems.

## Upgrade

Take a complete stopped backup including private runtime keys before upgrading.
The migration preserves old webhook configuration and delivery history, disables
legacy configurations and creates a disabled global integration. It sends no
notifications. Select the dispatcher, configure mappings and instructions, paste
credentials in the owner UI, test and explicitly enable. Enabling never catches
up existing tasks automatically.

## Integration limits

Grok documents Bearer-authenticated JSON webhooks, editable routine instructions
and asynchronous bot-to-bot handoffs. A real webhook-triggered handoff, instruction
read-back and busy-bot behavior must be verified in the user's account. Automated
Crew tests use synthetic fixtures and do not certify Grok Bot. HTTP acceptance
is not evidence that an agent started or finished the task.

See [webhook setup and execution](../webhooks.md) for the contract and recovery
procedure. Human review remains owner-only and never performs an external action.

Release validation also waits for the mapping form to be ready before editing it
in UI tests. The 0.4.0 candidate failed that Windows test before binary publication;
0.4.1 carries the corrected test without changing the integration behavior.
