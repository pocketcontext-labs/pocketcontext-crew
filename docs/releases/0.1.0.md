# PocketContext Crew 0.1.0

First Crew-specific binary release: shared memory buckets, versioned Markdown
notes, an AI Team task board, exact-draft human review, and one authenticated MCP
endpoint. External agents perform work; Crew does not post, send or pay.

## Native installation

Release archives contain `pocketcontext-crew` (`pocketcontext-crew.exe` on Windows)
and third-party notices. Fixed-version installers download only this repository's
assets and verify archive checksums. They require an explicit absolute project
directory, refuse existing executables without an observed-version replacement
opt-in, and refuse a pre-existing database without a Crew executable. Never use
an existing PocketContext database as a new Crew project.

Linux AMD64 and ARM64 binaries are static. The macOS ARM64 build requires macOS
15 or later and is ad hoc signed. The Windows AMD64 build is unsigned and links
its MinGW runtime statically. The recommended always-on native hosting procedure
is Linux with a domain, native HTTPS, an OS service and separately configured
backups. Native owner access uses a password or short-lived reader sign-in link;
SMTP and S3 are not native installation prerequisites. Remote MCP still requires
a reachable HTTPS domain; local installation alone does not expose it.

For runtime compatibility, command output and help retain the `pocketcontext`
name, the database is `pocketcontext.db`, and existing runtime environment variables
retain their `POCKETCONTEXT_` prefix. `--version` reports `pocketcontext 0.1.0`
with the release commit. Installer-only settings are `CREW_INSTALL_DIR` and
`CREW_REPLACE_VERSION`. The separately packaged container retains its internal
`pocketcontext` executable and its existing pinned image is unchanged.

## Release verification

The release workflow builds and tests all four native platforms, verifies binary
architecture/linkage, checks archive layout and provenance, and assembles a
checksum manifest. Publication verifies uploaded bytes before making the release
immutable. Follow-up jobs install the published assets and run synthetic Crew and
inherited infrastructure end-to-end tests. A workflow definition is not evidence
that a particular run passed: check the release's actual workflow result.

Automated checks do not establish a new domain's public certificate issuance,
owner browser sign-in, third-party client OAuth consent, or a particular host's
backup scheduling. Complete those checks for each deployed instance.
