# Crew 0.8.0

Agent commands for Crew installs without a domain.

## Work commands in the binary

Until now agents reached Crew only through remote MCP, which needs
`serve --headless --domain HOST --mcp`. An install on your own computer had no
agent path. The binary now carries five work commands, so it is both the
localhost server and the CLI that the installed skill calls, as in PocketContext:

| Command          | MCP tool    | Route                        |
| ---------------- | ----------- | ---------------------------- |
| `read JSON\|-`   | crew_read   | `POST /api/crew/read`        |
| `search JSON\|-` | crew_search | `POST /api/crew/search`      |
| `schema`         | crew_schema | `GET /api/crew/schema`       |
| `query JSON\|-`  | crew_query  | `POST /api/crew/query`       |
| `write JSON\|-`  | crew_write  | `POST /api/crew/agent-write` |

Each takes the MCP tool's input as one JSON object, as an argument or `-` for
standard input (useful on Windows and for long text). Input is validated against
the same schema as the MCP tool before any server is started or contacted, and
the CLI and MCP share the same request builders. Output is JSON on stdout.

The commands run locally with `--db` (the local key; the server starts when
needed) and on a computer paired through `tunnel serve` / `tunnel invite` with
`--url` (its saved session). `help COMMAND` documents each one.

## Agent route only

`write` never uses the owner route. CLI writes behave like MCP agent writes:
comments never wake anyone, reassignments count toward `max_bot_handoffs`, and
owner decisions, bucket archival, agent deactivation and credential entry are
refused (HTTP 403).

On an install without a domain, CLI agents act with owner authority: the local
key on the host, or the saved session token on a paired computer. The agent route
still applies, but the human-review boundary is enforced only for OAuth MCP
clients. The skill and docs say so; decide reviews yourself in the reader. There
is no local MCP endpoint and no new or unauthenticated route.

## Exit codes

0 ok; 1 HTTP or transport error, including 403 owner-only refusals and 429 rate
limits (the message names the seconds to wait); 2 usage or invalid input; 4 HTTP
409. On exit 4 the last stderr line says whether another request changed the
record first (reread, reassess, then retry) or Crew refused the operation with a
reason code such as `execution_required` or `handoff_limited` (do not retry it
unchanged).

## Limits

- Cloud assistants (Grok, Gemini web and mobile, ChatGPT and similar) cannot
  reach an install without a domain; they need public HTTPS MCP.
- Outgoing webhook wakes can be configured, but woken cloud bots cannot answer
  without public MCP.
- A paired computer keeps access through the tunnel address and its saved
  session. To remove one, rotate the address with `tunnel serve --new-address`
  and invite the computers you keep again.

## Documentation and skill

New [local use](../local.md) guide, exported in the manual. The skill's "Work
with Crew" section now uses the commands with the absolute binary and `--db` or
`--url`, and the MCP tools when the assistant is connected to an HTTPS `/mcp`.
The manual now names the release it ships with and links to its tag, and the
inherited PocketContext release notes moved to `docs/releases/upstream/`.

## Upgrade

No migrations. Follow the [upgrade procedure](../upgrades.md), then refresh
profiles and skills so agents get the new skill text.
