# Crew 0.5.0

The Grok integration now guides the owner through selecting an existing dispatcher,
copying one assistant setup prompt, entering credentials privately, acknowledging
a safe connection test, enabling delivery and checking real routing. Disabled
controls explain their prerequisites. Advanced configuration remains available.

## Discovery that works with cached connectors

Read `crew_read` collection `capabilities` for a versioned operation catalog and
input/result schemas. Current MCP discovery includes execution operations and
metadata fields. Clients with an older cached tool schema can send retry keys and
execution proof in `data._crew`; the server normalizes this envelope before the
same authorization, concurrency and fencing checks. Workers must stop if the
required operation cannot be used, never substitute an unfenced task update.

## Coordinated execution from the first write

`execution.begin` validates and acquires work atomically, returning the next step
and proof. Replayed begins return fresh state for reconciliation without granting
authority to send again or resume work. A task becomes governed when Crew enqueues a task wake. MCP writes to
that task require execution proof even before the first worker acquires it.
Governance persists through completion and invalidation; an owner can explicitly
set the task to Waiting to release it for ordinary work. Tasks that never entered
webhook coordination retain ordinary MCP behavior. Owner edits remain available.

A dispatcher handling another bot must report native handoff capability from the
actual routine context. Handoff preparation, reported send, recipient acquisition,
lease expiry and completion are separate evidence. Unknown send outcomes are not
retried automatically. External effects still require their own idempotency or
reconciliation; this is not a promise of exactly-once execution.

## Managed instructions and honest verification

A marked, versioned dispatcher block is compared exactly by SHA-256. Role and
reporting instructions live outside it and are preserved. Matching the managed
block no longer fails merely because Grok adds a reporting destination line.
Structured error codes distinguish instruction mismatch from revision conflict.
Synchronization and runtime capabilities remain caller-reported evidence; Crew
does not independently inspect Grok's routine settings or native message delivery.

## Upgrade and setup

Take a complete stopped backup including private runtime keys. The upgrade retains
the dispatcher, mappings, credentials and history, installs new managed instructions
and pauses delivery. It does not clear credentials, send tests or replay tasks.
Apply the new block through the copied setup prompt, run an explicit safe test and
inspect the runtime capability report, then enable. Routing checks use explicitly
authorized Ready sample tasks after enablement, not a disabled-delivery exception.

The server and synthetic platform tests cannot certify the user's Grok account.
Webhook-worker messaging availability and recipient behavior still need the live
setup checks. See [webhook setup and coordination](../webhooks.md).
