# Crew 0.6.0

Crew can now route a Grok webhook through its bot's parent conversation. The
routine reserves a parent wake and calls `WakeParent`; the parent handles its own
work or calls `SendToAgent(priority:true)` for the mapped recipient. One existing
bot keeps its usual role and serves as dispatcher, using one global webhook and
one shared Crew MCP connection. Direct routine dispatch remains available where
the routine itself has native messaging.

## Setup that verifies the actual route

Choose the dispatch path, paste webhook credentials directly into the owner
browser, and apply the versioned managed instructions through the copied prompt.
The parent-bridge connection test can target a mapped teammate while delivery is
disabled. It performs no task work and records routine acknowledgment, parent
receipt, reported send and automatic recipient acknowledgment separately. The UI
shows missing prerequisites and includes a direct bot-authorization prompt.

A recipient acknowledgment may arrive before the parent's send report; later
reporting preserves it. A new diagnostic cannot reuse old setup evidence. Bots
still need the owner's authorization for the Crew instance and intended work, and
their harness may require separate approval of tool calls. A successful diagnostic
is not a guarantee of unattended task execution or general delivery reliability.

## Durable bridge coordination

Protocol 3 adds `webhook_bridges` and the revision-checked
`webhook.bridge.prepare`, `parent`, `sent` and `ack` operations. Crew records an
attempt before the external wake or diagnostic send. A replay returns
reconciliation state rather than permission to call again. Current epoch,
destination, instruction, mapping and task eligibility checks reject stale work;
overdue acknowledgments remain visible uncertainty.

Both modern and legacy task-acquisition paths require parent receipt in bridge
mode. Task mutations still require valid execution proof, and human review stays
owner-only. Shared MCP attribution does not authenticate separate bots. Native
capability claims and message results are reported by the assistants; Crew makes
no exactly-once guarantee for external effects.

## Public development with UI hot reload

An explicit development mode supports authenticated public MCP and a hot-reloading
reader behind a reverse proxy such as Caddy. The backend and Vite listen only on
loopback, validate the public host/origin, and proxy same-origin secure HMR. The
frontend receives development settings rather than hosted credentials; Vite
restarts do not stop MCP. Ordinary production serving remains unchanged. See
[development](../development.md) for the opt-in flags and isolation requirements.

## Upgrade and validation

The migration preserves credentials, mappings and history, installs the new
managed block and pauses delivery without sending tests or backlog. Existing
integrations keep native mode until explicitly switched. Reapply instructions,
run a fresh diagnostic, then enable and verify authorized synthetic Ready tasks.
Take a complete stopped backup with private runtime keys before upgrading.

Synthetic tests cover the bridge lifecycle, duplicate-call guards, stale mappings,
expired deadlines, recipient fencing, atomic completion and migration
preservation. A development-account smoke test also completed one dispatcher task
and one mapped-recipient task, each with one fenced comment and atomic completion,
after direct bot authorization and scoped tool approvals. This verifies those runs,
not general provider reliability. Other accounts still require live validation.
See [webhook setup](../webhooks.md) and [upgrades](../upgrades.md).
